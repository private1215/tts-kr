# r22：3090 掉卡根因定位 + 训练降载方案（2026-10-07）

## 0. 结论先

**不是 PCIe 链路裕量不足。** 掉卡是 `SDES = Surprise Down`（设备从链路上整个消失），
而且是**零先兆**的：此前没有任何可纠正错误。链路裕量不足的表现应该是
BadTLP / BadDLLP / Replay 一路爬升再崩，实测**全 0**。

所以怀疑方向要换：**持续大电流下的供电 / 接触**，不是信号完整性。

已落地的缓解措施：**3090 功耗上限 350W → 250W**，并做成开机自启
（`deploy/gpu-powercap.service`）。带载验证：**250W 满载跑满 35 分钟，零错误**。

## 1. 原始日志（来自 `journalctl -k -b -1`，上次启动）

```

03:13:28 pcieport 0000:00:03.0: PCIe Bus Error: severity=Uncorrectable (Fatal),
                                type=Transaction Layer, (Receiver ID)
03:13:28 pcieport 0000:00:03.0:   device [8086:2f08] error status/mask=00000020/00000000
03:13:28 pcieport 0000:00:03.0:    [ 5] SDES                   (First)
03:13:28 nvidia 0000:04:00.0: AER: can't recover (no error_detected callback)
03:13:29 NVRM: Xid (PCI:0000:04:00): 79, GPU has fallen off the bus.
03:13:29 NVRM: Xid (PCI:0000:04:00): 154, GPU recovery action ... Node Reboot Required
```

逐条解读：

| 字段 | 含义 |
|---|---|
| `from 0000:00:03.0` + `(Receiver ID)` | 报错方是 **CPU 根端口自己**（Intel `8086:2f08`），不是 GPU |
| `type=Transaction Layer` | 事务层，不是物理层/数据链路层 → **不是电气信号质量** |
| `[ 5] SDES` | **Surprise Down Error**：下游设备从链路上消失 |
| `status/mask=00000020` | 只置了 SDES 一位，没有任何其他错误位 |

## 2. 排除「链路裕量不足」的三条硬证据

1. **整个 boot -1 里 Xid 只有 3 条**：79 ×1、154 ×2（03:13:29 同一秒）。
   没有任何早先的 Xid，也没有 `Corrected` / `BadTLP` / `BadDLLP` / `RxErr` /
   `Replay` / `MalfTLP` / `CRC` / MCE / thermal throttle。
2. **带载实测链路健康**：满载时 `current_link_speed = 8.0 GT/s`、
   `current_link_width = 16`、`Replays Since Reset = 0`、
   `aer_dev_correctable / fatal / nonfatal` **全 0**。
3. **拓扑上没有转接线/桥片**：
   ```
   -+-[0000:00]-+-02.0-[03]--+-00.0  RTX 3060
                +-03.0-[04]--+-00.0  RTX 3090
   ```
   3090 直连 CPU 根端口 `00:03.0`，中间没有 PCIe switch / riser。
   （记忆里「3090 占 M.2 链路」指的是**槽位与 M.2 共享通道**，
   不是转接线，本次已核实。）

🔑 信号裕量不足的典型时间尺度是**几秒到几分钟**，而且必然留下可纠正错误；
**30 分钟后一次性猝死**，时间尺度对不上。30 分钟正好是**供电端子 / 线缆 /
电源模块热积累**的量级。

## 4. 后续训练降载方案（已落地 + 建议）

### 已落地
- ✅ `deploy/gpu-powercap.service`（`Type=oneshot` + `RemainAfterExit`），
  开机自动 `nvidia-smi -i 1 -pl 250`。已 enable 且 active，实测生效。
  - 代价：算力下降约 15~25%。训练本来只要 1 epoch（见 §6），完全可接受。

### 建议（训练脚本侧）
| # | 动作 | 理由 |
|---|---|---|
| 1 | 训练前显式 `nvidia-smi -i 1 -pl 250` | 服务可能没起来（例如手动跑） |
| 2 | `save_per_step` 调小（每 30~50 步存一次） | 掉卡等于白跑，checkpoint 是唯一保险 |
| 3 | 训练时**不要**同时跑 cosy 在线推理 | 叠加负载 = 叠加电流 |
| 4 | 训练日志/监控写 `/mnt/tts/diag/`，**不要写 /tmp** | /tmp 重启即清空（本次教训） |
| 5 | 跑训练时开 `tools/pcie_watch.sh` | 真出问题时有逐秒证据，而不是只剩一条 AER |

### 需要现场确认（我远程查不到）
| # | 项 | 怎么看 |
|---|---|---|
| 1 | **电源额定功率与型号** | 3090(350W) + 3060(170W) + Haswell-E CPU(~130W) 满载轻松 700W+ |
| 2 | **3090 供电线是否一分二（daisy chain）** | 一分二是 3090 掉卡最常见的物理原因，应走两根独立 8pin |
| 3 | **机箱风道 / 显卡是否下垂** | 30 分钟热膨胀后接触不良也会表现为 Surprise Down |
| 4 | 电源是否服役多年（电容老化） | 老化电源在高负载 30 分钟后撑不住很典型 |

## 5. 顺带修的：评分脚本不再放 /tmp

服务器重启把 `/tmp/fidelity3.py` / `eval5r20.py` / `submit5.py` / `r18.py`
全清了，r20 的 93.52% 基线一度无法复现。**评分口径是验收标准，不能只存在于临时目录。**

已重建并固化进仓库：

| 文件 | 作用 |
|---|---|
| `tools/fidelity.py` | 还原度评分（11 项加权 + 六维测量 + LUFS/峰值/LTAS） |
| `tools/eval5.py` | 五案例线上验收驱动（`--prefix` 重评分 / `--submit` 重生成） |
| `tools/gpu_stress.py` | 可控时长/显存的 GPU 带载压测 |
| `tools/pcie_watch.sh` | PCIe / 供电 / AER 逐 10 秒监控 |

**口径校准（这一步最花时间）**：
- 静音占比 = **停顿总时长 / 总时长**。校验：案例 1a6c20 = 0.1875，
  与 `docs/r18` §7 记录的 0.188 一致。⚠️ 不能用帧级相对阈值（p25+6），
  那是相对阈值，两边都被推到 0.33~0.39，跟历史对不上。
- 音色 LTAS = **全局**长时平均谱、只取帧能量 **p35 以上**的有声帧、
  按总能量归一、只比 **1/3 倍频程（EQ 那 15 段，60Hz~11kHz）**。
  🔴 阈值 p50 → p35 是决定性的：p50 会把大量低能量帧（含我们 −120 dB 的
  数字静音）算进平均，高频被静音拉偏 3 dB（实测 1.70 → 0.75 dB）。

校准后重跑 r20 产物：**五案例均值 93.43%**，历史记录 **93.52%**，差 **0.09 pp**
→ 口径复现成功。
