### 2.2 `app/server.py`：音色名透传（开关 `TTS_OMNI_PERVOICE`，默认 0）
```python
def _omni_voice_of(job):
    g = "male" if _gender_of(job) == "m" else "female"
    if os.environ.get("TTS_OMNI_PERVOICE", "0")... not in ("1","true","yes","on"):
        return g
    return (job.get("voice") or "").strip() or g
```
- 调用点 `_synth_omni()` 从 `voice=("male" if ...)` 改为 `voice=_omni_voice_of(job)`。
- 备份 `server.py.bak-before-omnipervoice55`，md5 `4a2617e0…` → `7b46354d…`。
- 开关 drop-in：`qwen-tts.service.d/pervoice55.conf`（`TTS_OMNI_PERVOICE=1`）。

**开关关闭的行为验证**：L1 任务 `voice=EL_male` + 开关 0，omni 日志为
`synth voice=male(male)` —— 发出去的仍是性别，**与 v3.8 完全一致**。

### 2.3 `app/tts_engine.py`：Qwen prompt 缓存 key 加指纹（P2-b）

**音色增益可复现**（两条独立样本）：

| | 基线 | per-voice 第 1 条 | per-voice 第 2 条 | 增益 |
|---|---|---|---|---|
| 男 | 0.9518 | 0.9681 | 0.9695 | **+0.016 ~ +0.018** |

### 3.3 🔴 两个方法论结论（比上面的数字更重要）

1. **L3 的 ASR 相似度跑间波动 ≈ 0.12**。男声第一条 0.7629、第二条 0.8835，
   同一条链、同配置、只差一次采样，差 0.12；而同一文件**重跑 ASR 结果完全一致**
   （beam=5 是确定的）——所以这个波动是**生成侧采样**，不是 ASR 噪声。
   → **以后拿 L3 的 ASR 相似度下结论，差异小于 0.12 一律不算证据**；
   要么多次生成取均值，要么改用 CER（数字归一后）等更稳的口径。
2. **omni 没有传 seed**（`omni_client` body 只有 text/voice/rid），
   所以任何「同一文案 A/B」只要重跑一次就自带 0.1 量级的文本相似度噪声。
   这也解释了历史上多次「片段结论与全篇相反」的一部分原因。

## 4. P2：`language` / `normalize_text` 探针 —— 两条都不该开

`omni_server.py` 的 `SynthReq` 增加 `language` / `normalize` 两个可选字段，
环境默认 `TTS_OMNI_LANG`（空）/ `TTS_OMNI_NORM`（0），**默认仍不传**。

测法：同一段带阿拉伯数字的韩语文案，同音色，只改这两个开关。

| 变体 | 时长 | ASR 转写关键片段 |
|---|---|---|
| 不传（= 现网） | 12.56s | `29만 7천원` / `3.2%` / `1,830억원` |
| `language="Korean"` | 12.56s | 与上面**几乎逐字相同**（时长一模一样） |
| `+ normalize_text` | **11.52s** | `29만 7**영**원` ← 数字念错，且提速 8% |

- **`language="Korean"` 是空操作**：时长 12.56 对 12.56，转写无实质差别。
- **`normalize_text` 对韩语有害**：装 `num2words` 后 `297000 → 이십구만 칠천`，
  模型把 `칠천` 念成 `7영`，还整体提速 8%。
- 另记：不传 language 时 `normalize_text=True` 会走英文规范化器，
  `omnivoice` venv 没有 `WeTextProcessing` → **直接 500**（已实测）。
- 顺带装了 `num2words`（纯 python，小包），只为验证这一点；**生产不用**。

## 5. P1：OmniVoice LoRA —— 跑通了，但**这一轮没有产出值得上线的增益**

- `peft 0.21.2` 装进 `/mnt/tts/projects/omnivoice/venv`（`--no-deps`，最小 peft 冒烟通过）。
- 训练入口：`python -m omnivoice.cli.train --train_config … --data_config …`（accelerate）。
- 数据（`/mnt/tts/diag/omni_train/`）：

  | | 条数 | 时长 | 字/秒 |
  |---|---|---|---|
  | train | 225 | ≈39 分钟 | 7.57 |
  | dev | 31 | ≈6 分钟 | 7.70 |

  来源：`train_pick53.json` 精选案例的 `seg*.wav`，用 whisper 词级时间戳按自然停顿
  切 8–20s（`/tmp/mk_train55.py`）。
  🔴 **文本用的是我们自己的 ASR 转写**（对原始 `seg*.txt` 的 CER≈0.03）——原文是 250s
  整段、没有句级时间戳，硬对齐更容易切错。3% 字符噪声可接受，但**不是逐字真值**。
- tokenize 完：`tokens/train`（5 shard）、`tokens/dev`（5 shard），
  用模型自带的 `models/OmniVoice/audio_tokenizer`。
- 配置 `train_lora55.json`：`init_from_checkpoint=OmniVoice`、sdpa、
  `batch_tokens=2048`、`max_bs=4`、`grad_accum=8`、`lr=1e-4`、r16/α32。

### 5.1 🔴 训练在 150 步见顶，随即过拟合

| 步数 | dev loss |
|---|---|
| 150 | **3.7782** |
| 300 | 3.9012 |

dev loss 反向上升 → 400 步时主动停训，保留 `checkpoint-150`。
**原因清楚**：总数据只有 46 分钟、说话人只有 2 个，adapter 学到的是「这两个人的音色」，
不是「更自然的发声」。`lora_modules_to_save` 里还包含 `audio_embeddings` / `audio_heads`
（全量可训），进一步加速了对音色的记忆。

### 5.2 ckpt-150 的实测（同文案 200 字，base 与 adapter 各生成 2 条）

先定标测量噪声：同一配置两次生成，campplus 余弦本身波动 **±0.005（男）/ ±0.011（女）**。

| | base r0 | base r1 | adapter r0 | adapter r1 | 结论 |
|---|---|---|---|---|---|
| 男 | 0.9597 | 0.9643 | 0.9551 | 0.9624 | **−0.003，无效果**（两组完全重叠） |
| 女 | 0.9254 | 0.9148 | **0.9285** | **0.9318** | **+0.010**（adapter 两条都高于 base 两条） |

- 文本保真无退化：ASR 相似度 base 男 0.9105 / 女 0.9169 → adapter 男 0.9192 / 女 0.9169。
- 时长完全相同（23.36s / 26.12s）：时长由独立的 duration estimator 决定，与 LoRA 无关。
- scale 扫描（0.5 / 1.0 / 默认 2.0 = α/r）：**默认 2.0 最好**，调低反而变差
  （女 0.5→0.9162、1.0→0.9185、2.0→0.9285/0.9318）。与 Qwen 那边「scale 1.0 过冲」的经验**不一致**，
  说明这个结论不能跨模型套用。

### 5.3 判断

- 女声 +0.010 是真信号但**只有 per-voice 参考增益（+0.032）的三分之一**，
  且男声完全没有 → **不足以作为一次链路升级的理由**。
- 更关键的是：员工判「明显是机器」的那一维是**自然度**，campplus 测不出来。
  在只有 2 个说话人的数据上做 LoRA，本质上是在拟合音色而不是自然度。
- **要 LoRA 真正解决自然度，需要多样说话人的语料**（几十人以上），而不是同一个人的更多分钟。
  这条结论把 P1 从「下一步主线」降级为「需要换数据条件才值得再试」。
