# 声音克隆：机制、参数与排障手册

> 最后核对：2026-09-28（自动裁剪 + 音色列表上线后）
> 配套阅读：`README.md`（速览）、`CHANGELOG.md`（每次改动的实测数据）

## 一、员工视角：只需要做两件事

1. 上传整段录音（最长 15 分钟，不用剪）
2. 粘贴这段录音的**完整文字稿**（逐字对应）

其余全部由代码完成。录入成功后音色出现在右侧「已录入音色」列表，可试听、
可看文字稿、可删除重录，之后所有任务直接复用，**不用重新上传**。

## 二、服务端链路

```
POST /api/voices (name, ref_text, file)
  │
  ├─ 1. ref_text 非空校验 ───────────── 空 → 400「文字不能为空」
  ├─ 2. 读音频 / 转单声道
  ├─ 3. 时长校验 ─────────── <3s → 400 太短；>900s → 400 太长
  ├─ 4. sources/<名>__full.wav 留档原音频（换策略可重算）
  ├─ 5. voice_trim.trim_reference()
  │      ├─ 短时能量 + 自适应有声掩膜
  │      ├─ pick_window()  挑音质最好的 8~20 秒
  │      └─ slice_transcript()  文字按累计有声时长对齐截取
  ├─ 6. 写 voices/<名>.wav（成品片段，≤30s）
  ├─ 7. 截取后文字为空 → 400（宁可拦住，也不让坏音色混进来）
  └─ 8. 语速告警：字/秒 落在 2.5~10 之外 → 返回 warn（不拦截，前端黄色提示）

POST /api/jobs (mode=clone)
  ├─ 入队前校验：音色存在 / 有 ref_text / dur ≤ 30s，否则 400
  └─ run_job → tts_engine.synth_long()
        ├─ estimate_clone_prompt_tokens()  估算前缀长度
        └─ plan_generation(clone_prompt_tokens=...)  按显存反推 batch 上限
```

## 三、参数表

| 常量 | 值 | 位置 | 说明 |
|---|---|---|---|
| `REF_AUDIO_MIN_SEC` | 3.0 | `server.py` | 短于这个没法克隆 |
| `REF_AUDIO_MAX_SEC` | 30.0 | `server.py` | 成品音色硬上限（自动裁剪后必然满足） |
| `REF_AUDIO_BEST_SEC` | 15.0 | `server.py` | UI 给员工的建议长度 |
| `REF_AUDIO_TRIM_TARGET` | 15.0 | `server.py` | 自动截取目标长度 |
| `REF_AUDIO_AUTO_TRIM_ABOVE` | 30.0 | `server.py` | 超过才触发自动截取 |
| `REF_AUDIO_HARD_MAX_SEC` | 900.0 | `server.py` | 超过 15 分钟直接拒 |
| `TARGET_SEC` / `MIN_CLIP_SEC` / `MAX_CLIP_SEC` | 15 / 8 / 20 | `voice_trim.py` | 截取窗口 |
| `SNAP_SEC` | 0.60 | `voice_trim.py` | 边界在 ±0.6s 内吸附到能量最低点 |
| 语速告警区间 | 2.5 ~ 10 字/秒 | `server.py` | 超出给黄色 warn |

## 四、显存代价：为什么音频必须短

`voice_clone_prompt=[prompt] * n` —— **batch 内每个样本各背一份完整前缀**，
所以 prompt 长度按 batch 倍数放大 KV cache。

```
codec 帧率   = input_sample_rate / encode_downsample_rate = 24000 / 1920 = 12.5 Hz
prompt tokens = 音频秒数 × 12.5 + 文字字数 × 0.634
KV 单价      = 2(K,V) × 28 层 × 8 KV 头 × 128 维 × 2B = 0.109375 MiB/token
前缀 KV 合计 = 单价 × prompt_tokens × batch_size
```

实测（服务端真机读 `config.json` + `AutoTokenizer`，非估算）：

| 场景 | prompt tokens | 单样本 KV | batch 8 合计 KV | 生效 batch |
|---|---|---|---|---|
| 普通模式 | 0 | 0 | 0 | 8 |
| 克隆 15s | 269 | 29 MiB | 0.23 GiB | 8 |
| 克隆 25.74s | 445 | 47 MiB | 0.38 GiB | 8 |
| 克隆 30s（上限） | 516 | 56 MiB | 0.44 GiB | 8 |
| **克隆 329.33s（旧音频）** | **5423** | **593 MiB** | **4.63 GiB > 空余 4.14** | **5（旧版 8 = 必 OOM）** |

结论：**参考音频越长，显存按 batch 倍数涨**。30 秒是安全与效果的平衡点——
再长不只显存爆，长上下文注意力还会被稀释，音色相似度未必更好，
反而可能引入韵律漂移。

## 五、已踩过的四个坑（改代码前先看这里）

### 坑 1：`ref_text` 被 UI 标成"可选"，导致克隆 100% 失败

ICL 模式下 ref_text 是硬性必填，模型源码 `qwen3_tts_model.py:437` 对空串和 None
都抛 `ref_text is required when x_vector_only_mode=False (ICL mode). Bad index=0`。

更隐蔽的是 `run_job` 里 `v.get("ref_text") or None` 会把空串转成 None，
必然踩中校验。**任何"或 None"的写法在克隆链路上都是错的**。

### 坑 2：句子边界吸附两头外扩 → 文字变多 → 模型学错语速

这是最严重的一个，实测对照：

| | 修复前 | 修复后 |
|---|---|---|
| 10.5s 片段配的文字 | **130 字**（应有约 65） | **72 字** |
| 折算语速 | 12.4 字/秒 | 6.9 字/秒 |
| **生成实测语速** | **2.44 字/秒**（正常 6.15） | **7.17 字/秒** |
| 语速异常段 | 19 / 40 | 1 / 25 |
| **生成耗时** | **803 秒**（正常 143，慢 5.6 倍） | **185 秒**（慢 1.9 倍） |

机制：文字明显多于音频内容时，模型从 prompt 里学到一个错的语速，
表现为拖长音 / 重复（末段 14 个字念了 19.79 秒，正常约 2.3 秒）。

修复：吸附后超过期望 **1.5 倍就退回按词边界切**——宁可切在句中，也不要字数对不上。
同时把语速告警从 1.5~25 收紧到 **2.5~10**（原区间太宽松，放过了 12.4 字/秒的坏样本）。

> **重要区分**：用户报的"只念了一半"，实测覆盖度 94.2%（余下是空白/换行被规整），
> **文本并没有截断**。真正的症状是语速崩到 2.44 字/秒，让音频长度变成正常的 2.5 倍
> （702s vs 278s），听上去像"念不完"。排查时先看**覆盖度和语速**，不要先怀疑分段丢字。

### 坑 3：只按停顿边界选片段，会系统性错过最佳区域

一段"全程连续、没有停顿"的语音往往音质最好，但它**产生不了停顿边界**，
只按停顿选就会漏掉它。实测：选中的片段 cv=0.798，而漏掉的 271.5s 处 cv=0.229
（平稳得多）。

修复：停顿边界与滑窗两条路径**都跑**，停顿只给 1.08 加成、不作准入条件。

### 坑 4：前端 `applyStatic` 会整块覆盖元素

`applyStatic()` 用 `e.textContent = I18N[UI][key]` **整块覆盖**，
所以 `data-i18n` 元素内部**不能放任何子元素**——红色星号、图标都会被抹掉，
必须放在该元素**外面**做兄弟节点。

另外：`applyStatic` 遇到语言包里**没有定义的 key 就不替换**，
所以新增 key 必须四语（中英日韩）同时补，否则切换语言后界面会露出中文。

## 六、排障速查表

| 症状 | 先看这里 | 判读 | 处理 |
|---|---|---|---|
| 报 `ref_text is required ... ICL mode` | `voices.json` 的 `ref_text` | 为空/纯空白 | 重新录入，必须填文字稿 |
| 音色下拉显示「（不可用）」 | `/api/meta` 的 `voices_ok` | 缺文字稿 或 `dur > 30` | 用原音频重新录一次（会自动截取） |
| 生成音频比正常长 2 倍以上 | 日志里各段语速 | 语速 < 4 字/秒 | 检查音色的 `ref_text` 字数与 `dur`：字数/秒 应在 5~7 |
| 怀疑"没念完" | 服务日志「覆盖度异常」+ `stats.chars / len(text)` | ≥85% 属正常（空白被规整） | 真低于 85% 才是分段丢字 |
| 克隆任务 OOM | `plan_generation` 日志的 `clone_prompt_kv_total_gib` | 前缀 KV 是否接近显存余量 | 缩短参考音频；代码已自动降批 |
| 录入后黄色告警 | 返回的 `warn` 字段 | 语速落在 2.5~10 之外 | 核对文字稿是否真的对应这段音频 |
| 音色列表看不到/删不掉 | `renderVoiceList()` 是否被 `loadMeta()` 调用 | 未调用则面板不渲染 | 检查 `loadMeta()` 里是否调了列表渲染 |

## 七、关键数据位置

| 数据 | 路径 |
|---|---|
| 音色元数据（含 `clip` 截取区间、`src_dur`、`src_text_len`） | `/mnt/tts/data/voices/voices.json` |
| 成品参考音频（≤30s，实际用于克隆） | `/mnt/tts/data/voices/<名>.wav` |
| 原始长音频留档 | `/mnt/tts/data/voices/sources/<名>__full.wav` |
| 服务日志（录入 / 自适应 / 覆盖度） | `/mnt/tts/projects/qwen3-tts/service.log` |

> `voices.json` 目录属 `root:root`，`zheng` 账号无写权限。
> 手工写入需 `echo '<密码>' | sudo -S cp ... && sudo -S chmod 644 ...`

## 八、还没解决的

- **删除音色不清 `sources/`**：`DELETE /api/voices/{name}` 只删成品 wav，
  原音频（几十 MB）会残留。现网已有孤儿文件。
- **无 ASR 校验**：文字稿是否真的对应音频，只能靠语速告警间接判断。
  比例法依赖"文字稿逐字对应"这个前提，代码纠正不了内容本身。
