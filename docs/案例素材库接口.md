# 案例素材库接口（2026-10-05 新增）

## 1. 它解决什么问题

之前每次调优都靠**一两条**案例音频拍脑袋，样本太少、指标无法横向对比，
「1:1 保真」也就没法被证明。这个库把案例沉淀成数据集：

> 每份案例 = 原文 + 原声 + 自动算出的客观指标

攒够样本后，才能按性别/长度/说话人横向找规律，而不是反复试错。

## 2. 为什么独立成库，不并入 voices

| | voices（音色）| cases（案例）|
|---|---|---|
| 角色 | 克隆源，**输入** | 对标目标，**标准答案** |
| 时长 | ~15 秒（甜点）| 几分钟整段 |
| 用途 | 喂给模型当 prompt | 衡量我们还差多少 |

混在一起会让人分不清哪个是输入、哪个是判卷标准。所以物理和逻辑上都分开。

## 3. 存储位置

```
/mnt/tts/data/cases.json          索引（列表页读它）
/mnt/tts/data/cases/{cid}/
    seg{N}.wav        24kHz 单声道归一化音频（统一口径，后续分析不用猜采样率）
    seg{N}.txt        该段文本
    source{N}{ext}    原始上传留档（将来换分析口径不用重传）
    merged.wav        拼接整段（多段案例本来就是连着播的，韵律按整段算）
```

目录由 `CASE_DIR` 决定，随 `TTS_BASE` 走。换机只要改 `TTS_BASE`。

## 4. 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/cases` | 上传（可多段音频 + 对应文本）|
| GET | `/api/cases` | 列表，支持 `?gender=male\|female` 过滤 |
| GET | `/api/cases/{cid}` | 详情（含 segments 与 prosody）|
| GET | `/api/cases/{cid}/audio` | 下载音频，加 `?seg=N` 取指定片段 |
| GET | `/api/cases/{cid}/text` | 下载拼接文本 |
| POST | `/api/cases/{cid}/analyze` | 后台重算韵律六维 |
| DELETE | `/api/cases/{cid}` | 删除（管理员可删全部，员工只能删自己的）|

鉴权与其它接口一致：**先 Form 登录拿 cookie**。

## 5. 上传约定

`POST /api/cases`，multipart：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 案例名，如「案例-男声」|
| `gender` | | `male` / `female` / `unknown`（默认 unknown）|
| `source` | | **来源平台**，见下表（默认 unknown）|
| `tags` | | 自由标注，如 `model=v3;speed=1.0` |
| `note` | | 备注 |
| `files` | ✅ | 音频，可多个（mp3/wav/m4a 均可）|
| `text_files` | | 文本，可多个 |

`source` 取值：`elevenlabs` / `qwen` / `cosyvoice3` / `other` / `unknown`

> **为什么要标 source**：案例是「标准答案」，案例多来自 ElevenLabs。
> 只有标出平台（以及 voice/model/speed 这些生成参数），后面才能按参数
> 分组找规律 —— 否则不同平台的样本混在一起，结论会互相污染。

### 文本怎么配（两种都支持）

**① 逐段一一对应**：`1.mp3 / 2.mp3` 配 `1.txt / 2.txt`，排序后按序配对。

**② 一篇文案 + 多段音频**：`nan.txt` + `1.mp3 / 2.mp3`

这正是 **ElevenLabs 的产物形态**——整篇文案丢进去，平台按字数上限自动拆成
多块、逐块生成，所以拿到手就是「1 篇文案 + N 段音频」。

因此接口不会「存个整篇文案就完事」，而是**把文案按段拆开、对齐到每段音频**，
每段都记 `char_start` / `char_end`，能回溯到整篇文案的确切位置。这样：

- 每段有**准确**文本（不是 ASR 猜的，ASR 噪声 ~22%）
- 能算 CER 验证「这段音频是不是真念了这段文案」
- 能逆向研究平台的拆分边界策略

### ⚠️ 对齐为什么按时长占比，而不是按我们的 split_chunks

一开始我按 `pipeline.split_chunks`（2600 字上限、句末断开）拆文案去对音频，
结果对不上：

| | 第 1 段 | 第 2 段 |
|---|---|---|
| 音频时长 | 261.5 s | 222.3 s → **54% / 46%** |
| split_chunks 字数 | ~2600 字 | ~1445 字 → **64% / 36%** |

**两者差了 10 个百分点** —— 说明 ElevenLabs 的分块策略与我们不同
（而这正是要拆解的目标之一）。硬用字数块去套音频，文本范围根本不是
音频念的那段，CER 会爆掉，还会误判成「文本与音频对不上」。

所以实际采用**按时长占比切到最近句末**：时长占比才直接反映「这段音频
念了多少字」。同时把 `split_chunks` 的预测边界存进 `chunk_pred` 字段，
**两者的差异本身就是平台分块策略的直接证据**。

### 对齐方式（记在 `align_method`）

| 方式 | 触发条件 | 可靠性 |
|---|---|---|
| `per_file` | 上传时就按段给好了文本 | 最准，直接用 |
| `duration_ratio` | 一篇文案 + N 段音频，按时长占比切到句末 | 准（默认路径）|
| `none` | 对齐不了，退化成整篇文案 + 每段 ASR | 兜底 |

**没给文本的段都会自动用 ASR 转写补上**，标 `text_src="asr"` 供人工校对；
用户提供的标 `text_src="user"`。

### curl 示例

```bash
# 登录
curl -c ck.txt -X POST -d "username=admin&password=你的密码" \
     http://192.168.1.101:8000/api/login

# 上传（音频+文本，一一对应）
curl -b ck.txt -X POST http://192.168.1.101:8000/api/cases \
  -F "name=案例-男声" -F "gender=male" -F "note=ElevenLabs 原声" \
  -F "files=@1.mp3" -F "files=@2.mp3" \
  -F "text_files=@1.txt" -F "text_files=@2.txt"

# 只传音频，让 ASR 补文本
curl -b ck.txt -X POST http://192.168.1.101:8000/api/cases \
  -F "name=案例-男声" -F "gender=male" \
  -F "files=@1.mp3" -F "files=@2.mp3"
```

## 6. 入库时自动算的指标

**整段**：`total_dur`(秒) / `total_chars`(字数) / `cps`(字每秒)
**每段**：`dur` / `chars` / `cps` / `text_src` / `cer`
**韵律六维**（后台算，写完 `prosody` 字段并置 `prosody_done=true`）：

| 维度 | 含义 |
|---|---|
| A 句内动态 | 每句 F0 p15~p85 宽度中位 —— 有没有声调 |
| B 全局音高跨度 | 整段 F0 p5~p95 —— 用了多少音域 |
| C 能量动态 | RMS p10~p90 —— 有没有轻重音 |
| D 语速变化 CV | 3 秒窗音节密度变异系数 —— 语速是不是一路到底 |
| E 句尾多样性 | 每句末段斜率标准差 —— 尾声是不是一个调 |
| F 停顿熵 | 停顿时长分布熵 —— 停顿是不是只有一个长度 |

口径与 `app/prosody_report.py` 完全一致，所以**案例和我们的成品可以直接互比**。

## 7. ⚠️ CER 字段的陷阱（已处理）

`cer` 只在 `text_src="user"` 时计算，含义是「**用户给的文本与音频对不对得上**」。

不对 ASR 补的文本算 CER —— 那等于拿转写比转写，结果必然是 0，
会伪装成「文本完美匹配」，正好撞上本项目那条铁律
（**看到 CER 恰好为 0 = 回检坏了**），会误导后续分析。

判读：案例原声自己就有 **~0.2227** 的噪声底，明显高于它才说明文本对不上。

## 8. 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `TTS_CASE_PROSODY` | `1` | 设 `0` 关闭入库时的韵律自动分析 |

韵律用 pyin，几分钟音频要 1~2 分钟，所以**放后台线程跑**，
上传请求立即返回，指标稍后填充。

## 9. 实测（docs 自带的成对素材）

| 案例 | 时长 | 整篇字数 | 段数 | 对齐方式 | 各段 CER |
|---|---|---|---|---|---|
| 案例-男声 | 483.76 s | 4091 | 2 | duration_ratio | 0.1058 / 0.1068 |
| 案例-女声 | 459.13 s | 3429 | 2 | duration_ratio | 0.0380 / 0.0468 |

时长与 `ffprobe` 实测值完全一致，说明转码/拼接口径正确。
**CER 全部远低于 0.2227 噪声底**，说明文案确实被正确切分并对上了对应音频
（若用 split_chunks 硬套，CER 会明显爆掉）。

### 第一个有价值的发现：平台的实际分块比我们的 2600 上限更保守

| 案例 | 我们口径 `chunk_pred` | 平台实际边界 | 差异 |
|---|---|---|---|
| 男声 | 2573 / 4077 | **2185** / 4091 | 平台早切 ~388 字 |
| 女声 | 2581 / 3428 | **1888** / 3431 | 平台早切 ~693 字 |

两个案例同向：**ElevenLabs 每块约 1900~2200 字，而不是 2600**。
这正好是「拆解它是怎么生成的」要找的东西之一，数据现在已经沉淀在
`chunk_pred` 与实际 `char_end` 的差值里，攒够样本就能定出它的真实阈值。
