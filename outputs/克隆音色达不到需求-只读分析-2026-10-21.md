## 0. 结论先行

先把三件被混在一起的事拆开：

| 层 | 员工问的 | 当前代码怎么测 | 现状 |
|---|---|---|---|
| **音色身份** | 「像不像那个人」 | campplus 说话人余弦（16k） | 0.92~0.95，EL-EL 上限 0.985，差 0.03~0.06 |
| **自然度** | 「像不像真人 / 是不是机器」 | **没有指标** | z37 客观全平，员工仍 4/4 判「明显是机器」 |
| **需求口径** | 「听不出差别」 | 覆盖率 / CER / click / cps / 频谱 | 指标可以全绿，验收仍失败 |

**核心判断：**

1. **生产主链（omnivoice）的参考是「固定两段」，不是「你选中的那个音色模板」。**
   员工默认的 `EL_male / EL_female` 在 `voices.json` 里虽然有 15s 参考音频和
   `ref_text`，但 `_synth_omni()` 只把 `voice="male" / "female"` 发给 omni 服务；
   `omni_server.py` 里是**两个写死的 10s prompt 路径**
   （`prompt_sola_00b6a45a` / `prompt_yohan_1a6c20a6`）。
   ⚠️ 注意：**omni 不是「没有参考」**——它用的这两段参考本来就对着目标人；
   问题是参考**不可配置、不读 `voices.json`、不持久化**。所以改参考音频、
   重录音色、重新提取音色模板，对 omni 的输出**没有任何影响**。
   这是「怎么调都没用」的第一位原因，修法是「把 voice 做成可配置」，
   不是「补一个参考」。
2. **新案例 → 新音色的提取链路，恰好用了脚本作者自己标注为「错误做法」的组合。**
   线上 API 调 `mkcase_voices.py` 时没传 `--group-by embed`（按名字分组），
   又显式用 `--pick window`（挑最容易切的 15s，而不是最像本人的 15s），
   新音色还固定写 `engine=qwen`。真正被作者称为「正确做法」的
   `pick_source_centroid`（按说话人嵌入质心选段）**线上从未调用**；
   而 API 里「质心模式要上显卡」的理由是错的——campplus 用的是
   `CPUExecutionProvider`，脚本环境还把 `CUDA_VISIBLE_DEVICES` 清空了。
3. **当前主引擎没有任何说话人自适应。** OmniVoice 上游明确支持 LoRA 微调，
   案例库同人数据男 108.7 分钟 / 女 173.9 分钟，远超 10~30 分钟门槛；
   服务器上也有 `repo/training/` + `train_config_finetune_lora.json`。
   但生产**没有开**：`deploy/qwen-tts.service.d/lora.conf` 里
   `TTS_LORA_ADAPTERS=""`、`TTS_LORA_ALIAS=""`；而且这份 drop-in 服务的是
   **Qwen**，不是 omni。Qwen LoRA 的实测是 base vs adapter 互相似 0.9989
   （几乎没改变输出），没有上线。omni 的 LoRA 一次都没跑过，
   且服务器 venv **没有装 `peft`**（见 P0-3）。零样本身份天花板约 0.93~0.95，
   后处理补不上 0.985 的差距。
4. **员工真正判「机器」的主因不是音色/带宽/click。** v3.6→v3.7 把 8-10k 能量
   提高 58 倍、音色 +0.016，z37 员工仍判新旧同分、我们 4 段全 C、EL 2 段全 A。
   这说明继续在 16k/24k、EQ、click、参考切片上做微调，边际收益接近零；
   问题在自然度 / 微观韵律 / 模型本身的生成质量。
5. **「达到需求」在代码里没有可执行定义。** 生产任务只回检 CER（内容），
   不回检音色、不测量自然度；`engine_score_all.py` 是离线体检工具，
   `cmp_l3v35.py` 甚至完全不含音色列。也就是说：一个音色明显不对的成品，
   只要字念对了，照样会交付给员工。没有闸门，就没有闭环。

一句话：**不是「音色调得不够细」，而是「生产链用的不是你调的那个音色」+
「没有模型级自适应」+「验收测的不是员工在听的东西」三件事叠加。**

## 1. 需求与实际验收口径的差距

### 1.1 项目自己写的需求

`README.md` / `项目规范.md` 的口径非常明确：

- 唯一验收：同一条韩语文案，我们生成的 vs ElevenLabs 生成的，**员工听不出差别**。
- 员工零调参：只输标题 + 文案 + 选男女，其余系统决定。
- 验收只看长篇（L3，≥3~5 分钟）。
- 音色与质量是两件事：音色要贴近案例那个人，质量要达到案例水准。
- 判定线：覆盖率 <0.85 = 吞字；冗余率 >0.30 = 重复；音色 <0.90 = 偏低。

### 1.2 代码实际测的

| 环节 | 代码位置 | 实际测了什么 | 没测什么 |
|---|---|---|---|
| 生成后回检 | `app/server.py` `run_job()` → `asr_check.check_chunk()` | CER / 覆盖率（内容） | **音色、自然度** |
| 任务落盘 | `app/server.py:2302-2305` `files[]` | `cer` 一个数 | 无 `spk` / 无相似度 |
| 离线总评 | `tools/engine_score_all.py:107-111` | `spk`（campplus）+ 韵律 10 维 + CER/覆盖 | 自然度 / 微观音质 |
| L3 对比 | `tools/cmp_l3v35.py:90-105` | click / 质心 / 中频 / 杂音 / cps / 停顿 / CER / 覆盖 | **完全没有音色列** |
| 音色测量 | `tools/engine_score_all.py:65-71` | 一律转 **16k** 再算 campplus | 8k 以上、自然度 |

**关键结论：** 生产任务没有「音色不合格就拒绝/重试」的闸门。音色是线下报告里
人工补算的，不是交付链路的一部分。员工听到的成品，可能在音色上已经明显偏离，
但 `jobs.json` 里 CER 是 0.03，任务状态是 done。

### 1.3 阈值与「需求」不是一回事

- 同人判定：campplus ≥0.75（`tools/spkchk.py` 口径）。
- 偏低告警：<0.90（README）。
- EL 自己两条音频的余弦：**0.985**（`.workbuddy/memory/2026-10-20.md:372`）。
- 我们：v3.5 L3 **0.9362（男）/ 0.9238（女）**；v3.7 24k 男 **0.9518**、
  女 0.9195（`docs/r53-16k带宽瓶颈根因-2026-10-21.md`）。

0.93 对 0.75 是「同人」，对 0.985 是「明显不是同一段录音的水平」。项目没有定义
「要达到 0.96 还是 0.98 才算验收通过」，所以每轮都可以说「音色已经达标」，
但员工仍说「不像 / 机器」。**需求没有被翻译成一个可判定的数字。**

## 2. 当前实际生产链路（v3.7）

### 2.1 员工默认路径

```
员工点「男声 / 女声」
  → /api/meta 的 best_clone：male=EL_male, female=EL_female
  → /api/jobs mode=clone, voice=EL_male/EL_female
  → voices.json 的 engine=omnivoice
  → _synth_omni：只传 text + voice="male"/"female"
  → omni_server：VOICES["male"/"female"] 两个写死的 10s prompt
  → OmniVoice.generate()：内部按 15s 自动分块（audio_chunk_duration=15）
  → _run_fix_chain：--no-pitch --no-clean --no-adaptive-hf --eq anull
       + headfix + target-cps atempo + 响度 + 数字零填充
  → _mideq53b_wrap：全声部 +2dB @1.8k（默认，隐藏）
  → _clickfix53b_wrap
  → 24k → ffmpeg 44.1k → mp3 192k
```

### 2.2 代码地图（本地快照）

| 动作 | 位置 | 说明 |
|---|---|---|
| 默认音色 | `app/server.py:177` `BEST_CLONE` | `EL_male` / `EL_female` |
| 读音色参考 | `app/server.py:1196-1198` | 读进 `ref_audio` / `ref_wav_path` |
| 新引擎不分块 | `app/server.py:1256-1258` | `chunks=[全文]` |

### 2.3 这条链路实际「没有做」的事

- 没有把 `voices.json` 里那个音色的 `path` / `ref_text` 传给 omni。
- 没有为每个音色维护 prompt；omni 只有 male/female 两套。
- 没有给 Omni 传 `language="Korean"`，也没有 `normalize_text=True`。
- 没有走 `pipeline.normalize_korean` / `TTS_KO_NUM`。
- 没有音色相似度回检、没有自然度指标、没有音色闸门。
- 没有模型自适应（LoRA/adapter）。

## 3. 问题点（按影响排序）

### P0-1 生产 omni 的参考是「固定两段」：改参考音频/重录音色对输出无效

> 复审修正：原标题写「不使用音色模板」容易被读成「omni 不用参考」。
> 准确说法是：omni **用了参考**，但用的是两段写死的 10s 参考；
> 它**不读 `voices.json`、不按音色映射、不可持久化配置**。
> 修法不是「补参考」，是「把 voice 做成可配置」。

**现象**

- 管理员在「已录入音色」里试听 `EL_male.wav`（15s），听到的是 A；
  实际 omni 生成用的是 `prompt_yohan_1a6c20a6.wav`（10s），是另一个切片。
- 把某个音色的参考音频换成更好的 15s，或者重新录入同名音色，omni 输出不变。
- 把 `voices.json` 的 `engine` 改成 `omnivoice`，只是换了 omni 的 male/female
  固定 prompt，并没有换成该音色的参考。

**代码证据**

- `app/server.py:1196-1198`：确实把音色参考读进了 `ref_audio` / `ref_wav_path`。
- `app/server.py:1602-1605`：`_synth_omni()` 只传 `text` 和
  `voice=("male" if _gender_of(job)=="m" else "female")`，
  **没有把 `ref_audio` / `ref_wav_path` / `ref_text` 传给 `omni_client.synth()`**。
- `app/omni_client.py:72-74`：HTTP body 只有 `{"text":..., "voice":..., "rid":...}`。
- `deploy/omni_server.py:47-58`：`VOICES = {"female": prompt_sola..., "male": prompt_yohan...}`，
  路径写死。
- `deploy/omni_server.py:120-126`：`rw, rt = VOICES[req.voice]`，按 voice 名取死路径。

**影响**

- 这是「换参考音频 / 重录音色 / 重新提取模板」长期没有效果的**直接原因**。
  只要音色绑定的是 `omnivoice`，`voices.json` 里的 15s 参考就是死数据；
  omni 仍会用它的两段固定 10s 参考生成。
- 员工默认的两个音色即使没有换参考，也存在「试听片段 ≠ 实际 prompt」的认知偏差。
- 新说话人只要走 omni，就永远只会是 male/female 两个固定声音；
  这不是「克隆」，是「两个固定音色」。
- 🔴 但这**不等于**「omni 没参考 / 参考没用」：它的参考是 EL/Yohan 的切片，
  本来就对着目标人；所以当前 timbre 0.93~0.95 并不差。缺的是
  **per-voice 可配置能力**，不是「参考音频」本身。

**置信度**：高（代码直读，无需服务器验证）。
**需要服务器确认**：线上 `voices.json` 里 `EL_male/EL_female.engine` 是否确为
`omnivoice`；线上 `omni_server.py` 的 `VOICES` 是否被 `/voices` 运行时改过
（见 P1-1）。

### P0-2 新案例 → 新音色：线上用的是「按名字分组 + 最容易切 + qwen」

这条链路是「案例库 → 自动拆解 → 音色模板 → 任意文案」的核心。实际代码：

**（a）没有按声音聚类**

- `app/server.py:3600-3601`：
  `cmd = [python, mkcase_voices.py, "--apply", "--pick", "window",
  "--min-cases", N]`。
- **没有传 `--group-by embed`**；`tools/mkcase_voices.py:450-452` 的默认值是
  `--group-by name`。
- `tools/mkcase_voices.py:278-286` 的 `groups()` 按 `cases.json` 里的
  `name` 字段分组，不按 campplus 嵌入。
- 项目自己的注释（`tools/mkcase_voices.py:289-297`）写得很清楚：按名字会
  「同一人两个名字 → 拆两组；两个人共用一个名字 → 合成一组；一条案例里换人 →
  发现不了」。README 却写「按声音自动聚类」——**需求与线上调用不一致**。

**（b）没有用「最像本人」的 15s**

- API 显式 `--pick window`；`tools/mkcase_voices.py:407-431` 的
  `pick_source()` 只按「能截出最长片段」挑案例，`voice_trim.pick_window()`
  按「平均能量 × 稳定度 × 停顿惩罚」挑窗口（`app/voice_trim.py:73-160`）。
  这套分数**与说话人身份无关**。
- 真正的方法 `pick_source_centroid()`（`tools/mkcase_voices.py:208-250`）在注释里
  被作者称为「**这才是从案例里提取这个人的音色的正确做法**」：对同人所有素材
  滑窗提 campplus 嵌入，取质心，挑最接近质心的窗口。**线上没有调用它。**
- API 的理由是「质心模式要加载说话人模型上显卡，会和生成抢显存」
  （`app/server.py:3584-3586`）。这是**错误理由**：
  `tools/mkcase_voices.py:187-191` 用的是 `onnxruntime` 的
  `CPUExecutionProvider`；`app/server.py:3540-3549` 的 `_script_env()` 还把
  `CUDA_VISIBLE_DEVICES` 清空了。**质心模式本来就不上 GPU。**
- 结果：新音色的参考片段是「最好切的一段」，不是「最像这个人的一段」。
  这会直接拉低克隆相似度。

**（c）新音色固定走 qwen**

- `tools/mkcase_voices.py:565`：`"engine": "qwen"`。
- 员工默认 `BEST_CLONE` 仍是 `EL_male/EL_female`（`app/server.py:177`），
  新提取的音色不会自动成为默认；管理员要在高级面板里手动选，而且选了 omni
  也会被 P0-1 忽略参考。
- 也就是说：**「上传新案例 → 得到新克隆音色」这条路，要么走 qwen 零样本
  （天花板低），要么走 omni 固定男/女声（根本不是这个音色）。**

**（d）已有音色不重建**

- `tools/mkcase_voices.py:484-487`：命中 `KNOWN_SPEAKER` 就跳过；
  `KNOWN = {"EL_male": "1a6c20a60481", "EL_female": "00b6a45ad6aa"}`
  （`tools/mkcase_voices.py:87-91`）只给 EL_* 补 gender/bench_case，
  **不会重选参考音频**。
- 案例库从 10-07 的 5 条涨到 10-21 的 36 条（女 173.9 分钟），但
  `EL_male.wav / EL_female.wav` 还是 10-05 那一次切的 15s。
  **数据在增长，prompt 是冻结的。**

**影响**

- 新音色达不到需求，不是模型单点问题，而是「选段方法 + 分组方法 + 引擎路由」
  三处都走了弱路径。
- 这条链路是「案例库 → 音色模板」的产品承诺，线上实际没有按承诺执行。

### P0-4 验收指标与员工听感脱节：客观全绿，员工仍判机器

**证据**

- z37（`.workbuddy/memory/2026-10-21.md:246-269`）：
  `m_new C / m_old C / m_el A / f_new C / f_old C / f_el A / ctrl D`
  → 我们 4 段全判「明显是机器」，EL 2 段全判「像真人」；
  新旧同分 = 16k→24k 的改动完全不可闻。
- 复审又排除了三个维度：韵律（F0std / p90-p10 / cv / 包络 cv）、
  谐噪比 HNR、细粒度 LTAS，全部与 EL 持平。
- 这说明：**当前指标测的维度，不是员工判「机器」的维度。**
- `engine_score_all.py` 的 `spk` 是 campplus 说话人身份，不是自然度；
  `cmp_l3v35.py` 完全没有音色列；`run_job` 只有 CER。

**为什么会这样**

- campplus 是「说话人识别」模型，衡量「是不是这个人」，不衡量「像不像真人」。
  一个 0.95 的克隆可以非常像那个人，同时非常机器。
- click / 质心 / 中频 / 杂音 / cps / 停顿 / CER 都是**静态、全局、可平均**的量；
  员工感知的「机器」更多来自微观韵律、气声/呼吸、共振峰过渡、音素时长分布、
  相位/瞬态、句内重音等，这些当前指标没有覆盖。
- 反馈题是单段独立评分，隔几分钟听两段；项目自己已经记录
  「员工根本无法比较音高/音色」（`.workbuddy/memory/2026-10-17.md:1140-1150`）。
  用这种范式去判「音色 +0.02 / F0 +20Hz」，信噪比不够。

**影响**

- 团队会不断「优化一个员工听不出的指标」，然后得出「改了没用」。
- 复审修正：z25 的「换参考无效」**不能**再解释成「测试噪声把真改善淹了」。
  原始票是新旧参考全选 B；0.0276 余弦 / +20Hz F0 这个量级本身不可闻
  （与 z44 同结论）。所以 P1-1 的新参考是「客观更好、但听不出」，
  不是「被噪声投票误杀」。两者的后续动作相反：不要再去追参考级微调。
- 「一直达不到需求」的本质是：**闭环的反馈信号与需求不一致**。

**置信度**：高（z37 是直接证据；z25 原始票已复核）。

### P1-5（新增）Qwen 侧「参考文本泄漏」：新音色走 qwen 时的隐藏地雷

> 这条是上一版漏掉的，来自 `docs/r55-克隆参考文本泄漏-2026-10-21.md`
> 与同事的补充。它不影响当前 omni 主链，但影响「新音色走 qwen」的那条路。

**代码事实**

- `app/tts_engine.py:453-454`：`create_voice_clone_prompt(..., x_vector_only_mode=False)`
  固定走 **ICL 模式**，`ref_text` 会进入 prompt。
- 现役 `EL_male` 的参考是 15s / 160 字 ≈ **10.7 字/秒**；实际语速约
  8.5 字/秒（`tools/mk_z25.py:42` 的 10s ≈ 85 字口径）。
- `docs/r55` 实测：同文案、同 seed、3090，ICL 全文 160 字 →
  输出 29.28s / CER **0.431**，开头两句被当正文复读；
  xvec-only（不给 ref_text）→ 22.88s / CER **0.083**；
  截到 40 字 → 11.92s / CER **0.958**（漏读大半）。
- 女声同口径：xvec 24.40s / CER 0.137；40 字版 CER 0.973。

**机制判断（同事补充）**

- 不是「长度」问题，是「**配比超标**」：`ref_text` 字数 / 音频时长
  超过实际语速，模型会把 prompt 当正文继续念；截太短又会让模型
  学不到足够内容，反向漏读。
- 因此有一个**未被测过**的中间点：按参考音频的实际语速配比
  （15s ≈ 127 字，而不是 160 或 40），有可能既保留 ICL 的音色，
  又不复读。这个实验 3 分钟能跑完，值得做；但不能保证成功。

**影响**

- 新音色走 `mkcase_voices` 默认 `engine=qwen`，`ref_text` 若配比不对，
  会复读参考稿；而现网语速体检用「输入字数 / 时长」，复读会让 cps 变小，
  落在正常区间，**不会触发拒绝采样**（r55 原话）。
- 生产对 Qwen 没有「CER 超阈值就整单失败」的硬闸门；`ASR_MAX_RETRY`
  只重掷，最差结果仍可能交付。这不影响 omni 主链，但影响新音色。
- 历史 10-13 的「VoxCPM2/OmniVoice 胜出」是 A/B 择优；Qwen 当时若也在
  ICL 泄漏状态，它从未在公平条件下被评过（r55 §5）。

**置信度**：高（r55 实测 + 代码）；「127 字能修好」是待验证假设。

## 5. 建议的复审决策（不改代码，只定方向）

> 以下不是代码改动，是「如果要改，先拍板什么」。按依赖顺序排列。

### 5.0 复审后的最小改动优先级（采纳同事的建议，略作调整）

| 优先级 | 动作 | 为什么 | 前置条件 |
|---|---|---|---|
| **P0** | omni 的 voice 做成 **per-voice 可配置**（读 `voices.json` + 持久化 + 映射），顺手修 Qwen prompt 缓存 key | 所有「换参考/换音色/新说话人」的前提；不做这个，后面全是白改 | 先审计线上 `voices.json` 与 `/voices` 运行时状态；确认只保两个音色还是支持任意音色 |
| **P1** | OmniVoice LoRA（男 28.2 / 女 25.1 分钟精选） | 唯一可能跨过零样本 0.93~0.95 天花板的模型级路径；Qwen 的否决结论不能套用 | 服务器 venv 装 `peft`；确认 `repo/training/` 可跑；数据划分/去异类；先 1 条冒烟 |
| **P2** | omni 补 `language="Korean"` + 文本规范化 | 低成本、确定性最高；修「数字/单位/缩写」这一类硬伤 | 无；但要用含数字的财经稿 A/B |
| **P3** | 长文分块连续性 | 机制真实，但已有弱否证；不阻塞主线 | 先用句边界对齐点或员工听「相邻/跨界 15s」再谈 |
| **旁路** | Qwen ref_text 配比实验（15s ≈ 127 字） | 3 分钟可跑；若成立可救 qwen ICL 的音色；不成立就封存 | 同参考、同 seed、多 seed；只做离线/单任务，不动生产 |

> 如果短期只保 `EL_male/EL_female`，P0 的范围可以缩小为
> 「让这两个音色各自绑定自己的参考并持久化」，不必一次做通用 per-voice；
> 但 P0-2 的新音色链路仍然不能宣称「任意案例可克隆」。

### 5.1 先把「需求」定义成一个可判定问题

需要你拍板三选一（或组合）：

1. **身份优先**：目标 = 生成的声音听起来是 SOLA / yohan 本人。
   验收 = 与真实参考的 campplus ≥ 某阈值（例如 0.96）+ ABX 同人测试。
2. **自然度优先**：目标 = 员工听不出是 AI。
   验收 = 同文案 ABX / MOS，不把 campplus 当主指标。
3. **完全替代**：两者都要，且以员工盲听为准。
   验收 = L3 同文案多人 ABX + 音色/自然度分列，不再用单一「综合分」。

当前项目实际上是 3，但代码按 1 在优化、按 2 在做反馈，二者没有拆开。
**不先定义，后面所有改动都会重复「客观好了、员工不认」。**

### 5.2 先做一次「生产到底用了哪个 prompt」的只读审计

不需要改代码，只需要在服务器上核对：

- `voices.json` 里 `EL_male/EL_female` 的 `path`、`ref_text`、`engine`、`dur`。
- `deploy/omni_server.py` 的 `VOICES` 当前值，以及进程内存里是否被
  `/voices` 改过（对比 `omni.log` 的 `set_voice` 记录 / 重启时间）。
- `prompt_yohan_1a6c20a6.wav` 与 `EL_male.wav` 的 campplus 余弦、
  时长、F0、ref_text 是否逐字对齐。
- 最近一条员工任务日志里的 `synth voice=...`、`fix_chain` 输出、
  `mideq53b`、`clickfix53b`、`FIX_SR`。

**目的**：确认 P0-1 / P1-1 在线上是否成立，避免基于本地快照误判。

### 5.3 决定「音色模板要不要真正接进 omni」

这是 P0-1 的根。两条路线：

- **路线 A（小改，B/C 级）**：把 omni 的 voice 做成 **per-voice 可配置**：
  请求里带 `wav/txt`（或 voice id → 路径），服务端按音色取 prompt，
  缓存 + 持久化，读 `voices.json`。这样 `voices.json` 的参考才真正生效，
  新音色才能走 omni。
- **路线 B（不改架构）**：明确只支持 male/female 两个固定音色，
  删掉/隐藏「任意音色克隆」的产品承诺，避免继续在无效路径上投入。

⚠️ 注意：这不是「omni 缺参考」——它已经有参考；缺的是**可配置/持久化/映射**。
如果选 A，必须先解决 P1-1 的「参考怎么选、怎么持久化、怎么审计」；
否则只是把「固定两段」变成「可变的固定两段」。

### 5.4 决定「要不要做 OmniVoice LoRA」

这是唯一有可能跨过 0.93~0.95 零样本天花板的模型级路径。

- 数据：总量女 173.9 分钟 / 男 108.7 分钟；同事建议先用**精选**
  男 28.2 / 女 25.1 分钟（需核对这些数字的筛选口径），先剔除两个异类，
  再按案例/说话人划分 train/dev/test（不能同篇相邻切片泄漏）。
- 硬件：3090 24G；OmniVoice 0.6B 量级，LoRA 可训练参数约 3%，
  比 Qwen 1.7B LoRA（实测 7.72 GiB）更轻。
- 验收：同一批 L3 文案，base vs LoRA，**多 seed**，音色 + 自然度 +
  完整性同表；至少一个完整案例留出做 test。
- 风险：服务器 venv **没装 `peft`**；`accelerate` / 训练 manifest 需确认；
  数据是 EL 合成音，LoRA 可能学到 EL 的痕迹；官方 `sft_12hz.py` 的
  label-shift 补丁是否已打未知；需要先 1 条冒烟。
- **不建议**在没有 A/B 的情况下直接替换生产权重；
  也不要把 Qwen adapter 的「0.22 分不显著」直接套到 OmniVoice LoRA。

### 5.5 决定「韩语前端要不要补到 omni」

这是一个低风险、高确定性的修复方向：

- omni 请求带 `language="Korean"`（或 `ko`）。
- 在发 omni 之前走 `pipeline.normalize_korean()`（至少 `KO_NUMBER_UNIT`；
  `TTS_KO_NUM=1` 时走 `konum.normalize_numbers`）。
- 用同一篇含数字/百分比的财经稿做 A/B：base vs normalize，测 CER、
  数字读法、cps、自然度。
- 注意：`ref_text` 不要一起规范化（它必须与参考音频逐字对应）。

### 5.6 决定「隐藏 EQ / 固定 cps / headfix」的去留

这三项都是全局的，不是 per-voice：

- `_mideq53b_wrap` 的 +2dB @1.8k：如果保留，必须按音色验证；
  如果不确定，先做 per-voice A/B，而不是继续全局加。
- `--target-cps`：对 omni 是否应该强制到 EL 语速？对「克隆某个人」来说，
  说话人的自然语速是身份的一部分；强制锚定会抹掉这个身份。
- `_headfix_cut`：已知会误切真实首词（v3.4→v3.5 收紧过），
  对新音色/短首句仍要回归。

### 5.7 决定「验收要不要加音色/自然度闸门」

当前任务只在 CER 上拦。建议至少增加**只记录不拦截**的字段：

- 每个 chunk 的 campplus 与目标参考的余弦。
- 每个 chunk 的 F0 / 能量 / 停顿 / 频谱与目标案例的偏差。
- 任务级 `timbre_score`、`naturalness_proxy`（如果有）。
- 如果低于阈值，标记 `review`，不直接交付。

没有这个，P0-4 的闭环永远不会建立。

### 5.8 先修流程：仓库/服务器单一真相源

- 改代码前，先把服务器上的 `server.py / fix_chain.py / omni_server.py /
  qwen-tts.service / voices.json` 拉回本地，逐文件 diff。
- 所有补丁脚本（`deploy/patch_*.py`）要么进 git，要么在服务器上有
  「已应用」标记；不能靠记忆。
- `VERSION` 只能由 `release_version.py` 写；`voices.json` 的外部改动必须走
  `/api/voices/reload`，且要清 Qwen prompt 缓存（P2-1）。
- `POST /voices`（omni）要么加持久化 + 审计，要么禁用，只允许改配置文件。

### 5.9 建议做：Qwen `ref_text` 配比实验（3 分钟，离线）

同事提出：现役 `EL_male` 是 15s / 160 字 ≈ 10.7 字/秒，实际约 8.5 字/秒；
按实际语速配到 15s ≈ 127 字，可能既保留 ICL 音色又不复读。
我建议**做**，但把它定义成一次有明确判据的实验，不是「再试一次」：

- 变量：同一段 15s 参考音频，`ref_text` 分别取
  **160 字（现役）/ 127 字（按实际语速）/ xvec-only（不给）**。
- 固定：同目标文案、同 seed、同解码参数；至少 2~3 个 seed。
- 判据：CER < 0.15、时长比 0.9~1.1、无整句复读、音色不低于 xvec；
  任一不过就封存，不要只看音色。
- 注意：`docs/r55` 的 40 字版本是「截太短导致漏读」，127 字不是同一个实验；
  但 127 也可能落在敏感区，必须以 CER/时长为主判据。
- 生产不动：只跑离线/单任务，结果写回 r55 或当日记忆。

**我的建议**：如果短期只保 omni 的 `EL_male/EL_female`，这个实验优先级低
（旁路）；如果「任意案例可克隆」在范围内，它值得先做，因为新音色走 qwen
时这是直接的质量地雷。
